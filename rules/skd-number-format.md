# Формат чисел в отчётах своих блоков (СКД)

Правило проекта: во всех отчётах своих блоков (`Преф_`) числа выводятся **с двумя знаками после запятой**. Три знака — только там, где массовое округление заметно искажает итоги.

Применяется: при создании и правке любого своего отчёта на СКД.

---

## 1. Сколько знаков

**По умолчанию — 2 знака.** Формат задаётся **всем** числовым полям, включая целочисленные (`Количество`, `ДнейЭкспозиции`, флаги вроде `ПорогПревышен`): единый вид чисел во всех отчётах важнее, чем «12» вместо «12,00». Решение заказчика.

**3 знака — удельным величинам, которые дальше суммируются или умножаются.** Округление такого поля до двух знаков накапливается по строкам и уводит итог.

Пример: расход воды на ряд 4,1084747… суммируется по 59 рядам.

| Знаков | Расчёт | Итог | Факт |
|---|---|---|---|
| 2 | 4,11 × 59 | 242,49 | 242,4 |
| 3 | 4,108 × 59 | 242,37 | 242,4 |

Какие поля получают три знака:

| Поле | Почему |
|---|---|
| расход на ряд (план, факт) | складывается по рядам в расход крана |
| норма расхода на гектар | умножается на площадь |
| количество в сутки | усредняется по периодам |

Всё остальное — 2 знака: площади, стоимости, объёмы, температуры, нормы, отклонения, пороги.

Список полей с тремя знаками держите в самом правиле: агент сверяет с ним каждую новую схему.

---

## 2. ★ Формат задаётся В ДВУХ МЕСТАХ — это главная грабля

В схеме компоновки формат живёт на двух уровнях, и они конфликтуют:

1. **У поля набора данных** (`<field>` → `<appearance>`) — действует во всех вариантах сразу.
2. **В условном оформлении варианта** (`settingsVariant` → `conditionalAppearance` с пустым фильтром) — действует только в своём варианте, но **перебивает формат поля**.

**Если в отчёте есть готовые варианты настроек с правилами формата, менять только поле набора бесполезно** — оформление варианта его перекроет. Проверено: правка поля на `ЧДЦ=3` не дала эффекта, пока то же поле оставалось в правиле варианта с `ЧДЦ=2`.

Порядок действий при смене числа знаков одному полю:

1. Поменять формат **у поля набора данных**.
2. Проверить правила условного оформления **в каждом варианте**: если поле перечислено в правиле с другим форматом — **убрать его оттуда** и добавить для него отдельное правило с нужным форматом и пустым фильтром.

Итоги (`totalField`) собственного формата не имеют — наследуют формат своего поля по `dataPath`.

## 3. Два синтаксиса записи формата

В схемах встречаются оба, и оба валидны:

```xml
<!-- строкой -->
<dcscor:value xsi:type="xs:string">ЧДЦ=2</dcscor:value>

<!-- локализованной строкой -->
<dcscor:value xsi:type="v8:LocalStringType">
  <v8:item><v8:lang>ru</v8:lang><v8:content>ЧЦ=15; ЧДЦ=2</v8:content></v8:item>
</dcscor:value>
```

При поиске форматов в файле искать по подстроке `ЧДЦ=`, а не по конкретной разметке.

---

## 4. Порядок элементов в блоке поля значим

`<appearance>` идёт **последним** элементом блока `<field>`, после `<field>` и `<title>`:

```xml
<field xsi:type="DataSetFieldField">
  <dataPath>ПланЛНаДерево</dataPath>
  <field>ПланЛНаДерево</field>
  <title>…</title>
  <appearance>…</appearance>   <!-- здесь -->
</field>
```

Вставка между `<dataPath>` и `<field>` ломает соответствие XSD.

**Ловушка при скриптовой правке:** закрывающий тег блока — это строка, где `</field>` стоит одна. Внутренний `<field>Имя</field>` содержит ту же подстроку, и наивный поиск `</field>` срабатывает на нём. Условие должно быть `^[ \t]*</field>[ \t]*$`.

Вторая ловушка: `<dataPath>Имя</dataPath>` встречается не только в полях набора, но и в блоках `<totalField>`. Ограничивать обработку блоками, открытыми тегом `<field xsi:type=`.

---

## 5. EDT не видит внешних правок `.dcs`

Схема, изменённая мимо EDT, в build-модель не попадает: перед выгрузкой в базу нужен **F5 (Refresh)** на проекте, иначе в ИБ уйдёт старая схема.

---

## 6. Как проверить покрытие

Сплошная сверка по всем своим отчётам — какие числовые поля имеют формат:

```bash
cd <проект>/src/Reports
for d in Преф_*; do
  f=$(ls "$d/Templates/"*/Template.dcs 2>/dev/null | head -1)
  [ -f "$f" ] || continue
  echo "=== $d"
  grep -n "dataPath\|ЧДЦ" "$f" | grep -B1 "ЧДЦ" | grep dataPath
done
```

Критерий: у каждого числового поля формат есть, поля из таблицы §1 имеют три знака.

## 7. Правка `.dcs` мимо конструктора: что EDT НЕ ловит

Схема, собранная скриптом, проходит `revalidate_objects` и `get_project_errors` **чисто**, а падает уже при выгрузке в базу. EDT проверяет модель, а не соответствие XDTO-схеме платформы.

### `<title>` обязан нести тип

```xml
<!-- НЕВЕРНО: EDT молчит, платформа падает -->
<title><v8:item><v8:lang>ru</v8:lang><v8:content>Текст</v8:content></v8:item></title>

<!-- ВЕРНО -->
<title xsi:type="v8:LocalStringType"><v8:item>…</v8:item></title>
```

Без `xsi:type` платформа считает содержимое `anyType`:

```
Исключение XDTO при чтении Template.xml
НачалоСвойства: title   Тип: {http://www.w3.org/2001/XMLSchema}anyType
```

**Приём:** новый узел не сочинять, а копировать соседний такой же из этого же файла вместе со всеми атрибутами. Перед выгрузкой — сверить, что у всех однотипных узлов одинаковый набор атрибутов:

```bash
grep -o '<title[^>]*>' Template.dcs | sort | uniq -c
```

Разнобой в выводе = найденный дефект. Готовая проверка — `scripts/check_dcs_nodes.py` в этом репозитории.

## 8. Параметр не появится в шапке без `userSettingID`

Параметр из `dataParameters` варианта попадает в быстрые настройки формы, только если у него есть `<dcsset:userSettingID>` с GUID. Без него параметр существует, отчёт работает, но полей ввода в шапке нет — пользователь не может задать период или отбор, не открывая настройки.

При переносе схемы из эталона сверять наличие `userSettingID` у каждого параметра с уже принятым отчётом, а не только состав параметров.

Рядом же — `<use>Always</use>` необязательному параметру-отбору: без него пустой отбор даёт «Не задано значение параметра».

**`<valueListAllowed>true</valueListAllowed>` — только для параметров, которые в запросе стоят под `В (&Параметр)`.**
Параметру-границе (`ГОД(День) >= &ГодС`) платформа при восстановлении настроек подставляет пустой *список значений*,
и запрос падает: «Нельзя сравнивать поля неограниченной длины и поля несовместимых типов». Модуль отчёта может
подменять пустое значение, но это не спасает при компоновке мимо объекта отчёта и при списке, введённом пользователем.
Исправление — `valueListAllowed=false` у параметров-границ.

## 9. Ресурс не выводится в детальных записях

Поле, объявленное ресурсом (`<totalField>`), считается только на группировках. Если структура варианта — плоский список детальных записей, колонка ресурса пуста во всех строках. Симптом: поле есть в выборке, формат задан, а в отчёте пусто.

Лечится либо группировкой, либо снятием поля с ресурсов.

**Что важнее:** ресурсом должно быть только то, что осмысленно складывать. `Объем` работ с единицей измерения в соседней колонке складывать нельзя — итог сложит штуки, часы и гектары в одно число (на практике это давало «459 345,10» в итоге группировки).

### Как быть, если поле всё же нужно и на группировках

Снять с ресурсов — не всегда выход: тогда на группировках колонка пустеет совсем, а в структуре из одних группировок (без детальных записей) поле исчезает везде.

Правильный приём — **ресурс, который отдаёт значение только когда единица одна**:

```
ВЫБОР КОГДА КОЛИЧЕСТВО(Различные ЕдиницаИзмеренияРаботы) > 1
     ТОГДА NULL
     ИНАЧЕ Сумма(ОбъемРаботы)
КОНЕЦ
```

Работает на всех уровнях сразу: где разрез по единице есть — обычная сумма, где единицы смешались — пусто вместо бессмысленного числа. Не требует менять структуру вариантов.

Приём не выдуман: так же решает задачу типовой отчёт БИТ.ФИНАНС `бит_ПланФактныйАнализЗаявокНаРасходованиеДенежныхСредств` для сумм в разных валютах (`КОЛИЧЕСТВО(Различные Валюта) > 1`). Валюта там — то же, что здесь единица измерения.

Проверено на данных: в сводном варианте (группировки без единицы измерения) объём пуст, в вариантах с разрезом по единице — считается как раньше.

**Где искать такой дефект:** вариант отчёта, где ресурс выводится, а поля-разреза нет среди группировок. Проверять по всем вариантам схемы, а не по одному: в том же отчёте два варианта из трёх были корректны, дефект жил только в сводном.
