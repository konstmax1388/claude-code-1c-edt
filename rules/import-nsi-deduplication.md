# Создание НСИ при импорте: как не плодить дубли

Правило появилось после того, как одна и та же ошибка была найдена в проекте **четыре раза подряд**, в четырёх разных импортах. Каждый раз симптом был разный, причина — одна.

Применяется: при доработке любого импорта, который заводит элементы справочников по данным из файла.

---

## Ошибка, которая повторяется

```bsl
КлючЭлемента = ВРег(ТекстИзФайла);              // (1) кеш по СЫРОМУ тексту
СозданныйЭлемент = Созданные.Получить(КлючЭлемента);

Если СозданныйЭлемент <> Неопределено Тогда
    Строка.Элемент = СозданныйЭлемент;
    Продолжить;
КонецЕсли;

Объект = Справочники.Имя.СоздатьЭлемент();       // (2) создание БЕЗ проверки в базе
```

Два дефекта:

1. **Кеш по сырому тексту.** «Имидан.ВДГ» и «Имидан,ВДГ» в одном файле — разные ключи, создаются оба.
2. **Перед созданием справочник не проверяется.** Код доверяет результату распознавания, сделанного на этапе разбора. Если распознавание не сработало (другое написание, поиск по точному совпадению), элемент заводится заново — при каждой загрузке.

Второй дефект коварнее: он не виден на первом импорте и вылезает на повторном.

---

## Правильная схема

```bsl
// 1. Ключ кеша — нормализованный
КлючЭлемента = Преф_ИмпортВызовСервера.КлючСравненияНаименования(Текст);
СозданныйЭлемент = Созданные.Получить(КлючЭлемента);
Если СозданныйЭлемент <> Неопределено Тогда
    ...
    Продолжить;
КонецЕсли;

// 2. Последний рубеж: поиск в базе по тому же ключу
Существующий = ЭлементПоНормализованномуНаименованию(Текст);
Если ЗначениеЗаполнено(Существующий) Тогда
    Строка.Элемент = Существующий;
    Созданные.Вставить(КлючЭлемента, Существующий);
    ЗапомнитьСоответствие(ВидСоответствия, Текст, Существующий);   // чтобы в следующий раз нашлось сразу
    Продолжить;
КонецЕсли;

// 3. Только теперь создаём
```

Функция ключа — одна, экспортная, в общем модуле; её переиспользуют все импорты. Своя нормализация в каждом импорте — та же ошибка в новом месте.

**Что снимает ключ:** пробелы, знаки препинания и кавычки; латинские буквы-двойники `ABCEHKMOPTXY` приводит к кириллице.

Реальные пары из базы, которые этим ловятся: «Квад - Глоб ВР» / «Квад-Глоб ВР», «CЕРЕНАДА» с латинской C / «СЕРЕНАДА», «Тейя КС» / «Тейя, КС», «Имидан.ВДГ» / «Имидан,ВДГ».

---

## Что НЕЛЬЗЯ нормализовать, и почему

| Соблазн | Почему нельзя |
|---|---|
| Сравнивать по префиксу | склеит «Вуксал Кальций» и «Вуксал КальцийБор» — разные удобрения |
| Отбрасывать форму препарата (ВР, КЭ, СК, ВДГ) | «Микадо, КЭ» и «Микадо, СК» — разные формуляции с разной нормой расхода |
| Ловить опечатки расстоянием редактирования | «Нитрат калия» и «Нитрат кальция» отличаются двумя буквами и являются разными веществами |

Опечатки (`Кароген` при живом `Кораген, КС`) и синонимы (`Водорастворимое NPK Старт 13:40:13` при `SOLAR СТАРТ 13:40:13`) машина от настоящей разницы не отличит.

**Решение:** не блокировать импорт, а писать в протокол список похожих — по префиксу и по расстоянию редактирования не больше двух. Решает человек.

---

## Ключ должен включать различающий реквизит

Если справочник допускает одинаковые наименования у записей разного назначения — реквизит входит в ключ.

Пример: справочник показателей обследования — один и тот же показатель у двух видов обследования это **разные записи** с разными нормами. Ключ: наименование + вид обследования.

Обратный пример: справочник, который сам пересобирает наименование в `ПередЗаписью` (ловушки: место + вредитель). Наименование, построенное импортом, с ним не совпадает, поэтому ключ — набор реквизитов, а не наименование. В одном ряду стоят две ловушки на разных вредителей, и вредитель входит в ключ.

## Распознавание по тексту: грабли

- **Поиск по началу наименования без упорядочивания берёт случайного кандидата.** «Голден» → «Голден Рейнджерс (КФХ)»,
  и документы ушли не на тот элемент. Правило: среди совпадений по `ПОДОБНО "текст%"` брать **самое короткое**
  наименование (`УПОРЯДОЧИТЬ ПО ДЛИНАСТРОКИ(Наименование)`).
- **Буква в номере — это другой элемент.** «6А», «6Б», «6В» — три элемента с одним числовым номером; поиск по номеру
  складывал всё в первый. Букву разбирать отдельно и искать по полному наименованию.
- **Латиница в данных справочника.** Элемент «6A-1» с латинской A поиском по «6А-1» не находится. Это данные, не код,
  но ключ с заменой двойников ловит и это.
- **Запомненное соответствие переживает исправление кода.** После починки распознавания старое соответствие
  продолжало подставлять неверный элемент: поиск по запомненным соответствиям идёт первым. При исправлении
  распознавания проверять и чистить регистр соответствий по затронутым текстам.
- **Один блок дважды на листе** (те же показатели в двух колонках) даёт документ с дублями строк и «Запись с такими
  ключевыми полями существует» при проведении; документ остаётся непроведённым молча. Перед загрузкой снимать дубли
  по ключу строки.
- **Год из двух цифр** («08.08.24») при разборе даёт 0024 год — обходить `Год < 100 → +2000`.

## Чеклист для нового импорта

- [ ] Ключ кеша нормализованный, не `ВРег(сырой текст)`
- [ ] Перед `СоздатьЭлемент()` есть поиск в базе по тому же ключу
- [ ] Найденное записывается в `ЗапомнитьСоответствие` — следующий импорт найдёт сразу
- [ ] В ключ входят реквизиты, различающие однофамильцев (вид обследования, вредитель)
- [ ] Похожие элементы попадают в протокол предупреждением, а не молча создаются
- [ ] Проверено **повторным** импортом того же файла: второй прогон не создаёт ничего

Последний пункт обязателен: первый импорт всегда выглядит корректно, дубли появляются на втором.
