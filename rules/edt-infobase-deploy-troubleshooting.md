# EDT → инфобаза: применение конфигурации и диагностика падений

Правило по выгрузке/применению конфигурации из EDT в инфобазу и по диагностике падений при обновлении БД. Выстрадано на восстановлении одного из своих блоков (серверная база БП КОРП, ~2026-08) после аппаратного сбоя сервера.

Применяется: при «Обновить конфигурацию базы данных», падениях конфигуратора на реструктуризации, рассинхроне EDT↔ИБ, восстановлении после сбоев. Дополняет `edt-zip-export-pitfalls.md` (ошибки загрузки ИБ, Configuration.mdo).

---

## 1. Инкрементальная синхронизация EDT↔ИБ ХРУПКАЯ для структурных изменений

**Симптом:** при «Обновить конфигурацию БД» — `Неизвестный объект метаданных Document.X` (переползает по объектам) или `нельзя добавлять объекты метаданных без загрузки родительского объекта`, при этом EDT-модель ЧИСТАЯ (revalidate/get_project_errors без реальных ошибок).

**Причина:** EDT хранит снимок «что уже выгружено в ИБ». Краши, ручные restore базы, аварийные перезагрузки ломают соответствие снимок↔база → инкремент шлёт несогласованный пакет (ссылается на объекты, которых в базе нет).

**Фикс:** **ПОЛНАЯ перезапись конфигурации** (не инкремент). Для структурных изменений (новые документы/регистры) — раз в порцию делать полную выгрузку; инкремент оставить для правок кода.

**НИКОГДА не поднимать EDT-проект (исходники) из бэкапа** — там наработки, потеряешь их. Восстанавливать только ИНФОБАЗУ (данные) либо перезаписывать конфиг из EDT в базу.

## 2. Конфигуратор тихо падает на «Обработка структуры БД» (реструктуризация)

**Симптом:** конфигуратор или EDT-агент **вылетает без внятной ошибки** на 0% «Обработки структуры базы данных»; в EDT — `Потеряно соединение с агентом конфигуратора / Designer agent has closed communication channel`.

**Диагностика — НЕ гадать, снять факты:**
- **Windows Event Log → Application → Application Error / Windows Error Reporting:** имя сбойного приложения (`1cv8.exe`), **сбойный модуль** (напр. `backend.dll`), код исключения (`0xc0000005` = Access Violation).
- **Техжурнал 1С** — `logcfg.xml` в `C:\Program Files\1cv8\<версия>\bin\conf\` (нужной версии платформы! у клиента и кластера версии могут отличаться):
  - Сначала узкий: `<dump create="true" location="..." type="0"/>` + `<log>` с EXCP/EXCPCNTX.
  - Если не видно операции — все события: `<log ...><event><ne property="name" value=""/></event><property name="all"/></log>`.
  - Читать **хвост лога процесса** (`<logdir>\1cv8_<PID>\...log`) перед строкой `OSException`.

**Частая причина на БОЛЬШОЙ СЕРВЕРНОЙ базе:** лавина серверных вызовов `IFolderFileHost.open` (~сотни тысяч — чтение/сравнение всей конфигурации через сервер) → `Outgoing connection closed` → AV. Это **НЕ** память (проверить: конфигуратор x64 + свободная RAM), **НЕ** диск, **НЕ** данные (DBCC чист), **НЕ** наш код (EDT-модель валидна). Платформенный путь применения конфига к большой серверной базе не выдерживает объём обращений.

**РЕШЕНИЕ (проверено, сработало):** пакетная перестройка НА СЕРВЕРЕ:
```
"C:\Program Files\1cv8\<версия>\bin\1cv8.exe" DESIGNER /S "srv:port\Ref" /N"user" /P"pass" /UpdateDBCfg -Server /Out "C:\tmp\updatedb.log" /DisableStartupDialogs /DisableStartupMessages
```
Флаг `-Server` = реструктуризация серверной стороной (rphost). Сервер **доводит перестройку до конца**, даже если клиент-конфигуратор падает на финальном обмене (вылет косметический). Проверить успех: «БД не требует обновления» + объекты видны в Предприятии (перезапустить сеанс — командный интерфейс кешируется). Пустой `/Out` при этом — норма (туда пишутся только ошибки).

**Альтернатива (100% обход):** файловая база — `/DumpIB file.dt` → загрузить в файловую ИБ (`/RestoreIB`) → F7 там (локально, без серверных round-trip'ов) → `/DumpIB` обратно → `/RestoreIB` на серверную базу.

*(PowerShell: команду, начинающуюся с пути в кавычках, запускать через оператор `&`.)*

## 2.1. Полный сценарий восстановления после падения агента (проверено 2026-09-09)

Разбор одного дня целиком: от ошибки обновления до рабочей базы. Каждый шаг стоил времени, поэтому
порядок здесь — не теория, а протокол.

### Симптом на входе

После аварийного завершения сервера обновление конфигурации БД падает:

```
Ошибка загрузки/выгрузки конфигурации
Неизвестный объект метаданных - Report.<Имя>.Template.<Макет>
```

Стек: `importIncrementalXmlToInfobase` → `IncrementalInfobaseConnection` → `OnDemandSynchronizationStrategy`.
Это разд. 1: снимок EDT рассогласован с базой. Объект в проекте цел (проверить: файлы на месте,
XML парсится, объект в `Configuration.mdo`, `get_project_errors` пуст) — ломать проект не надо.

### Шаг 1. Полная выгрузка вместо инкремента — и чем она кончается

`update_database` с `fullUpdate=true` (или полная выгрузка из EDT). На большой серверной базе идёт
десятки минут; клиент MCP отвалится по своему таймауту **раньше** — это не отмена, работа продолжается.

Реальный ход в этом случае: 07:38 принят вызов → 07:42 «Загрузка конфигурации в информационную базу»
→ **09:04** «Обновление конфигурации базы данных» (конфигурация принята, началась реструктуризация)
→ **09:07** `DesignerDisconnectException`, «Потеряно соединение с агентом конфигуратора», вызов
завершается ошибкой через 89 минут.

**Важно:** к моменту падения конфигурация в основную уже загружена. Начатую реструктуризацию
доводить полной выгрузкой заново не нужно — достаточно завершить обновление БД (шаг 3).

### Шаг 2. ★ Смотреть активность ТОЛЬКО своего кластера

Здесь легко потерять час. На машине живут несколько версий платформы, у каждой свой `ragent` и свои
`rphost`. Нагрузка чужого кластера выглядит точно так же, как своя, и создаёт ложное впечатление,
что «сервер доводит перестройку».

Определять свои процессы по версии в пути и по порту регистрации:

```powershell
Get-CimInstance Win32_Process -Filter "Name='rphost.exe' OR Name='ragent.exe' OR Name='rmngr.exe'" |
  ForEach-Object {
    $v = if ($_.ExecutablePath -match '8\.\d+\.\d+\.\d+') { $matches[0] } else { '?' }
    [PSCustomObject]@{ Имя=$_.Name; PID=$_.ProcessId; Родитель=$_.ParentProcessId; Версия=$v
                       Аргументы=$_.CommandLine }
  } | Sort-Object Версия | Format-Table -AutoSize
```

Свои — те, у кого версия совпадает с версией базы, а `-regport` равен порту своего кластера;
`rphost` привязаны к своему `ragent` через `ParentProcessId`.

Пример этого стенда (2026-09-09): три кластера — 8.3.27.1719 (`regport 1541`), 8.3.27.1859
(`regport 3541`) и наш **8.5.1.1507 (`regport 5541`)**. У нашего был **ровно один** `rphost` (13208),
и он всё это время простаивал, пока три чужих `rphost` кластера 1541 грузили по 3–4 ядра.

Вывод, который стоит держать в голове: **загрузка `rphost` без проверки версии и порта не значит
ничего.** Сначала опознать свои процессы, потом мерить.

### Шаг 3. Пакетная перестройка на сервере

```
"C:\Program Files\1cv8\<версия>\bin\1cv8.exe" DESIGNER /S "srv:port\Ref" /N"user" /P"pass"
   /UpdateDBCfg -Server /Out "<лог>" /DisableStartupDialogs /DisableStartupMessages
```

Запускать только через `Start-Process` (см. память проекта `1c-batch-run-start-process`).
Флаг `-Server` перекладывает реструктуризацию на `rphost`, минуя клиентский агент — то самое звено,
которое отвалилось.

### Шаг 4. ★ Освободить базу от переоткрывшегося агента EDT

Первый запуск, скорее всего, упрётся в:

```
Ошибка блокировки информационной базы для конфигурирования.
С этой информационной базой уже работает конфигуратор:
компьютер: <хост>, сеанс: N, начат: <время>, приложение: Конфигуратор
```

Причина неочевидная: **EDT поднимает агент конфигуратора заново** — сам, без операции. В разобранном
случае агент упал в 09:07, а в 09:31:43 появился новый процесс `1cv8.exe DESIGNER` на той же базе;
он ничего не делал (6,7 с CPU за всё время), но держал монопольный доступ.

Найти и снять:

```powershell
Get-CimInstance Win32_Process -Filter "Name='1cv8.exe'" |
  Where-Object { $_.CommandLine -match 'DESIGNER' -and $_.CommandLine -match '<имя базы>' } |
  ForEach-Object { "PID $($_.ProcessId)"; Stop-Process -Id $_.ProcessId -Force }
```

Снимать безопасно, когда панель «Состояние» в EDT пуста и в `.metadata/.log` нет активной операции:
такой агент — просто удерживаемая сессия. После этого повторить шаг 3.

### Шаг 5. Проверка результата

Успех виден в `/Out`:

```
Обновление конфигурации базы данных
Обработка структуры базы данных...
Принятие изменений...
Обновление конфигурации базы данных успешно завершено
```

Пустой `/Out` — тоже успех (туда пишутся только ошибки); текст появляется, когда была реструктуризация.
В разобранном случае перестройка заняла **6 минут** против 89 минут безрезультатной работы EDT.

### После: EDT остаётся рассинхронизированным

`get_applications` продолжит показывать `INCREMENTAL_UPDATE_REQUIRED` — обновление шло мимо EDT, его
снимок об этом не знает. На работу базы это не влияет, но при следующем обновлении из EDT появится
модал «Изменения конфигурации информационной базы».

Отвечать **Override** (`externalInfobaseChanges=override`) — проект перезаписывает базу.
**Никогда Import**: он затянет состояние базы в исходники проекта и затрёт работу.

## 3. Повреждение базы после аппаратного сбоя

**Симптом:** после краха сервера (скачок питания и т.п.) — «неизвестный объект», падения реструктуризации, `Нарушено условие уникальности данных / duplicate key` при создании индекса.

**Диагностика:**
- `DBCC CHECKDB('база') WITH NO_INFOMSGS, ALL_ERRORMSGS` — физическая целостность SQL (пустой вывод = 0 ошибок = чисто).
- **Тестирование и исправление ИБ** (Конфигуратор → Администрирование) — логическая/ссылочная целостность 1С + реиндексация (DBCC этого НЕ видит; часто разблокирует реструктуризацию).

**Дубль уникального ключа** (напр. код справочника `_ReferenceNN`, индекс `_ReferenceNN_2`): найти в MSSQL два элемента с одинаковым кодом → поменять код одному / удалить дубль → повторить обновление.

## 4. Порядок диагностики «не применяется / падает обновление БД»

1. **EDT-модель чистая?** `revalidate_objects` + `get_project_errors` (реальные ошибки, а не фоновые ложные «не определена переменная … [Толстый клиент]» — их тысячи по всей БП, они не наши).
2. **Объект в `Configuration.mdo`?** (file-drop .mdo не регистрируется сам — см. `edt-zip-export-pitfalls.md` разд. 2).
3. **Целостность базы:** DBCC CHECKDB + Тестирование и исправление ИБ.
4. **Ресурсы:** диск (БД/лог/tempdb), RAM, разрядность конфигуратора (x64).
5. **Точная причина краха:** Windows Event Log + техжурнал 1С (разд. 2).
6. **Своя ли это нагрузка?** При нескольких кластерах на машине — опознать свои `rphost` по версии
   платформы и `-regport` перед любыми выводами об активности (разд. 2.1, шаг 2).
7. **Не держит ли базу агент EDT?** `1cv8.exe DESIGNER` на этой базе блокирует пакетное обновление;
   EDT поднимает его заново сам (разд. 2.1, шаг 4).
8. **Применение:** полная выгрузка / `/UpdateDBCfg -Server` / файловая база.

Сессия 1С кеширует конфигурацию и командный интерфейс — после обновления **перезапускать сеанс**.
